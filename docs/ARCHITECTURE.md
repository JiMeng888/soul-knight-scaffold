# 架构拆解：元气骑士式框架是怎么搭的

> 本文是对**公开技术资料 + 通用 Roguelike 工程实践**的归纳，以及本脚手架的实现对照。不涉及、也不依赖原作二进制。

## 0. 一句话结论

元气骑士（Unity3D / 2D 像素 / Sprite + Tilemap / Pixel Perfect）真正值得复用的不是某个类，而是六条架构决策：**数据驱动、基类+状态机、单例对象池、房间图生成、双状态分离、战斗三件套**。下面逐条对应到本项目的文件。

## 1. 分层与依赖方向

```
        ┌──────────────────────────────────────────────┐
        │  表现层  render/ ui/                          │
        │  Renderer · SpriteAtlas · HUD · Overlay       │
        │  只读逻辑层状态，通过 events 订阅变更           │
        └───────────────┬──────────────────────────────┘
                        │ 单向依赖（禁止反向）
        ┌───────────────▼──────────────────────────────┐
        │  逻辑层  world/ entities/ weapons/            │
        │  Room · Level · Player · Enemy · Projectile   │
        │  只认 GameCtx 接口，不认 Game 具体实现          │
        └───────────────┬──────────────────────────────┘
                        │
        ┌───────────────▼──────────────────────────────┐
        │  数据/状态层  data/ state/ core/               │
        │  配置表 · RunState · GameState · RNG · Pool    │
        └──────────────────────────────────────────────┘
```

关键手段是 `core/types.ts` 里的 `GameCtx`：逻辑层每个 `update(dt, ctx)` 拿到的都是接口，不是 `Game` 单例。这样 UI 换掉、引擎换掉，实体代码一行不用改。事件总线让「逻辑发生了什么」和「谁在听」解耦——逻辑层永远不知道 HUD 存在。

## 2. 六块核心，逐一对照

### 2.1 数据驱动

原作 355 把武器、几十个角色，靠的是配置表而不是继承树。`data/weapons.ts` 里 `WeaponData` 描述伤害/射速/弹数/散布/能耗/穿透，`WeaponSystem` 是唯一一份通用开火逻辑。近战之所以 `energy: 0`，是刻意留作弹尽粮绝的退路——能量池全局共享，让「带什么枪」成为资源决策而不是冷却计时。

**加一把枪 = 加一条数据。**

### 2.2 基类 + 状态机

`Entity` → `Player` / `Enemy` / `Projectile` / `Pickup`。玩家状态 `idle | move | roll | hurt | dead`，敌人 `idle | chase | windup | attack | laser | recover | dodge | dead`。可破坏物、宝箱、掉落物共用 `Damageable` 契约，伤害只传 `DamageInfo`。

一个反面教训（来自公开的同类复刻项目）：把 `Attack` 状态放进玩家控制器是多余的，因为攻击实际由武器执行；`CloseWeaponRange` 这类字段一旦没人读，还会反向限制近战范围。**状态机里只放真正有消费者的状态。**

### 2.3 对象池

子弹、敌人、掉落、粒子全部走 `core/ObjectPool.ts`。实现是「失活标记 + 每帧 `sweep()` 原地压缩」，不做 `splice`、不 `new`。弹幕密集时这是抗 GC 抖动的关键。原作还叠加了 Sprite Atlas / 动态合批 / GPU Instancing，本项目用 `SpriteAtlas` 把占位精灵预绘到一张离屏 canvas，呼应同一思路。

### 2.4 房间图生成

`world/DungeonGenerator.ts`：5×5 网格，中心入口，主干只走**正交步**，分支只能挂死叶子，门图严格是一棵树。`world/RoomTemplate.ts` 用 ASCII 描述房间内部，尺寸固定 15 / 21 / 25（同层统一尺寸，保证门中心线重合、走廊直连）。

`Level` 持有整层所有 `Room` 实例，过门 = 传送到邻居房间 + 相机直接对齐到新房间的跟随位置（见 §2.8），**没有场景加载，也没有状态需要序列化**。`(levelSeed, roomId)` 派生独立 RNG 子流，同种子完全可复现。

### 2.5 双状态分离

`RunState`（血盾蓝、武器、层、金币、击杀）与 `GameState`（宝石、升级、解锁、统计）严格分开。死亡时只重置 `RunState`；`SaveManager` 只把永久成长落盘，用 tmp → bak → 正式档的原子写入，并留 `version` 迁移分支。混在一起的典型 bug 是「死亡把永久升级也丢了」。

### 2.6 战斗三件套

Hitbox / Hurtbox / Health 收敛为 `Damageable.applyDamage(DamageInfo)`。两条容易静默出错的规则都写进了代码：

- **阵营 mask 分离**：玩家子弹只遍历 enemies，敌人子弹只打 player。共用一个 mask 会让一方永远打不中，且完全不报错。
- **子弹打墙用射线步进**：把一帧位移拆成 ≤ `TILE/2` 的小步逐点检测。高速子弹一帧走的距离超过墙厚，Area 重叠检测会直接穿墙。

### 2.7 计时 / 天赋 / 商店：三条新增数据流

- **计时**：`RunState` 存 `elapsed`（整局）与 `levelElapsed`（本层），只在 `mode === 'playing'` 时累加 —— 天赋、商店、暂停面板期间天然冻结，不靠额外的 `if (paused)` 补丁。切层时把 `levelElapsed` 交给 `GameState.recordLevelTime()`，最佳单层落盘；老存档由 `migrate()` 的 `{...base, ...d}` 补默认值 0，不炸档。HUD 只读状态，不反向写。
- **天赋**：`data/talents.ts` 是纯数据，27 条天赋 × 15 个 stat，用 `effects: { stat, add|mul }[]` 声明，唯一消费者是 `RunState.applyTalent()`。倍率字段各自有真实读取点：`damageMul` / `fireRateMul` / `critDamageMul` → `WeaponSystem`，`energyRegenMul` / `armorRegenMul` / `rollCdMul` / `hpRegen` → `Player`，`pickupRangeMul` → `Pickup`，`coinGainMul` → `RunState.addCoins()`，`shopDiscountMul` → `Game.buyShopItem()` 与 `Panels.drawShopPanel()`（显示与扣款共用 `shopPrice()`）。`applyTalent()` 的 `switch` 末尾有 `never` 穷尽检查 —— 以后往 `TalentStat` 加维度却忘了接消费者，`tsc` 直接报错。

  进层流程被 `pendingLevel` 挂起：每通过 `talentInterval` 层（当前 = 1，即**每层结束都能自选**），弹 `talentChoices` 张卡（= 4）。候选由 `rollTalentChoices()` 抽取：**优先给本局没拿过的**，27 条池子前 6 层不重复，拿光后才允许叠加 —— 纯随机三选一在每层都弹时会很快反复出同一批。`shuffle` 由调用方注入，data 层不依赖 RNG，函数可单测。
- **商店 / 奖励房**：`RoomType.SHOP` / `BONUS` 是无敌人房（常规为挂在主干上的叶子；极端布局下由兜底「就地改类型」产生，见 §4.1）。货位存在 `Room.shopStock` 上（跟随房间实例，玩家反复进出仍是同一批货、同一份已售标记），商品效果由 `Game.applyShopEffect()` 落地，`data/shop.ts` 保持纯数据。面板由 `ui/Panels.ts` 统一绘制，`cardRect()` 同时供绘制与 `hitCard()` 点击命中使用 —— 共用一份坐标，不会出现「画的框和点的框不是同一个」。

### 2.8 相机跟随：分轴钳制，而不是锁房间中心

视口固定 480×270，房间外框却是 272 / 368 / 432px 的正方形。这个尺寸关系决定了相机不能简单处理：

- **只锁房间中心**（早期实现）：房间比视口高，27 格房间南北门距中心 208px，而视口半高只有 135px。玩家走到门口时连人带门一起出屏，表现就是「看不到场景出口」。加个 12% 的玩家偏移也无济于事 —— 相机最多挪 25px，缺口还有 48px。
- **完全自由跟随玩家**：`Level.draw()` 只画当前房间，镜头会把大片房间外的纯色背景带进画面。

`render/camera.ts` 的 `cameraTarget(player, room, viewW, viewH, margin)` 是纯函数，按轴独立决策：

| 轴 | 房间 vs 视口 | 策略 |
|---|---|---|
| 纵向 | 房间 272~432 > 视口 270 | 相机在 `[origin + half - margin, origin + size - half + margin]` 内跟随玩家，玩家贴到哪边，那边的门就进入画面 |
| 横向 | 房间 272~432 < 视口 480 | `lo > hi`，锁房间中心。整间房本来就在画面里，追人只会把它推向一侧 |

`Renderer.followRoom()` 每逻辑步把目标交给 `moveCamera()` 做指数平滑（`cameraLerp: 4.5`，约 0.22s 时间常数），这就是「缓慢」的来源 —— 玩家不会被钉死在屏幕正中。**切层 / 换种子 / 过门用 `snapToRoom()` 直接对齐**：过门是「把玩家传送到对侧门」，相机若还从旧位置插值要飞近半个网格（~300px），期间玩家会跑出屏幕；房间内的缓慢跟随不受影响。

`cameraTarget()` 不 import `Room`，只依赖 `{ origin, worldW, center }` 最小契约，所以 `npm run verify` 能用普通对象在 Node 里逐点校验：三种房间尺寸 × 85 个玩家位置 = 255 采样点，断言玩家始终在视口内、站到门口时该门可见、纵向视口不越房间边界超过 margin、窄轴锁中心，并保留一条「旧 12% 跟随确实会丢人」的对照断言。改了相机或房间尺寸，这条会直接变红。

### 2.9 交互优先级：武器不能被传送门抢走

出口房清完怪后，`Room.clear()` 把传送门放在**房间正中**，而 BOSS 的武器掉落写在 `Enemy.die()` 里、落在尸体位置（`pos.y + 18`）。BOSS 又是会追人的，经常死在中心附近，于是武器和传送门只差十几像素、双双落在交互半径内。

`pickInteractTarget()` 早期只按距离取最近的一个，结果就是：玩家想捡 BOSS 掉的枪，按 `E` 却被传进下一层 —— 这是**不可逆**操作，那层没捡的武器直接没了。只靠生成时「拉开距离」也不可靠：拾取范围天赋能把半径放大 3 倍，而且 BOSS 死在哪是随机的。

修法是把仲裁从「取最近」改成「取最高优先级」：

```
score = 距离² × bias         // 越小越优先
bias  = gear 0.7 / service 0.85 / portal 1.5   // balance.ts: interactBias
```

- `bias = 1` 时完全退化为旧的「取最近」，所以原有候选（宝箱 / 神龛 / 商人）行为不变。
- 传送门给 **>1** 的权重，等于让它「让着」所有交互物；装备给 **<1**，两者距离接近时装备稳赢。
- 为什么不用「武器绝对优先」的硬分档：满两把枪的玩家可能根本不想要地上那把（`addWeapon` 会替换当前手持），硬优先会逼他先捡、还可能换掉手上的好枪。软权重保证「重叠时装备胜出」，但传送门明显更近时仍能直接进门 —— 玩家用站位就能表达意图。

生成层再做一道视觉保险：BOSS 掉落武器沿「远离房间中心」方向推到至少 3.5 格外（`Enemy.die()`），提示文字不再和传送门叠在一起。但**正确性只依赖权重**，位置只是好看。

`interactBias(kind)` 放在 `entities/Pickup.ts`（kind → bias 映射），数值在 `balance.ts`，纯函数仲裁在 `core/interaction.ts` —— 三者都不依赖 DOM，`npm run verify` 用三个用例锁死：重叠时选武器、武器稍远（1.25 倍）仍优先、武器远很多时让位传送门。

### 2.10 武器品质：概率与配色，而不是强度等级

品质解决的第一个问题是「玩家如何一眼判断掉落值不值得捡」。做法是把颜色收进单一事实源 `data/rarity.ts`：

```ts
RARITIES: { common/fine/rare/epic/legendary → { name, color, weight, minLevel, power } }
RARITY_ORDER: 从低到高，同时用于比较与过滤
```

HUD 武器名、拾取物光晕与边框、获得通知的文字颜色，全部调用 `rarityColor()`，页面里不写任何品质色值。这样加一档品质只改一个文件，不会出现「HUD 是蓝的、掉落物是紫的」。

**品质不直接决定数值**。如果史诗武器一律比精良强，品质就退化成了等级，武器的差异只剩数字大小。这里 24 把武器逐把调数值，品质只影响两件事：掉落概率、名字颜色。稀有武器的强度来自机制（穿透 / 爆炸 / 追踪），而不是把伤害乘以系数。

掉落曲线在 `rarityWeight()` 里按层数修正：

| 品质 | 基础权重 | 解锁层 | 修正 |
|---|---|---|---|
| 普通 | 46 | 1 | 每层 −2.2，下限 6 |
| 精良 | 30 | 1 | 每层 +0.6 |
| 稀有 | 15 | 2 | 每层 +1.4 |
| 史诗 | 7 | 4 | 每层 +1.1 |
| 传说 | 2 | 6 | 每层 +0.5 |

`minLevel` 是硬门槛：1 层无论权重怎么滚都不会出传说，否则开局就能把成长曲线打穿。`rollWeapon()` 还有两级降级 —— 抽到的品质在当前层不可用（`rarityWeight === 0`）就往下退；某档品质没有可掉落武器也往下退；全空才退回手枪。**任何情况下都返回合法武器 id**，不会把 `undefined` 一路传到 `addWeapon()` 才炸。

武器机制全部由通用逻辑实现，`WeaponData` 只是多几个可选字段：

| 字段 | 行为 | 实现位置 |
|---|---|---|
| `burst` / `burstGap` | 一次扳机连发 N 发，能量按总量预扣 | `WeaponSystem.update()` 的连发队列 |
| `bounce` | 撞墙按轴翻转速度分量，斜射进墙角不会卡死 | `Projectile.update()` 分轴反射 |
| `explode` / `explodeDamage` | 命中或引信结束时结算一次半径伤害 | `Projectile.explode()` |
| `homing` | 限速转向最近目标（不是瞬锁） | `Projectile.turnToward()` |
| `lifesteal` | 近战命中按次数回血，封顶最大生命 | `WeaponSystem.fireOnce()` |
| `arc` | 近战扇形半角，圣剑接近半圆 | 同上 |

一个必须写死的规则：**爆炸弹不结算直击伤害**。早期想「直击 + 爆炸」都吃，结果同一目标被算两份，调数值时根本看不出伤害来自哪一份。现在 `checkHits()` 命中后直接引爆并 return，伤害只由 `explode()` 按阵营过滤结算一次。

### 2.11 敌人：走位与攻击解耦

早期 `EnemyData` 把「怎么走」「怎么打」混在 `ai` 一个字段里，加一种攻击就要在 `update()` 里再塞一个 `case`。现在拆成两层：

- `ai`：`chaser / charger / shooter / orbiter / sentinel`，只决定位移；
- `attacks: EnemyAttack[]`：每条声明 `kind / windup / damage / count / spread / blast / length / duration / summonId / range / recover`，按顺序轮换。

`update()` 只推三段状态：`windup`（站定、持续瞄准、画预警）→ `execute`（按 kind 落地）→ `recover`（后摇，可缓慢移动）。BOSS 的 `attacks` 有多条，所以「守卫」会扇形弹与榴弹交替，「巨像」会激光接环形弹幕 —— 加阶段只是往数组里加一条，不用改状态机。

六种攻击形态：

| kind | 行为 | 关键约束 |
|---|---|---|
| `melee` | 近距离直接结算，带粒子 | 前摇 ≥ 0.1s，给玩家反应 |
| `shot` / `spread` | 单发 / 扇形弹幕，`count` + `spread` 控制 | 子弹走敌方阵营，只打玩家 |
| `grenade` | 慢速弹，`life = 1.5` 做引信，落地或到时爆炸 | 爆炸只伤玩家，不误伤同伴 |
| `laser` | 前摇画预警线，随后 0.3s 光束按 0.15s 节拍结算 | 前摇 ≥ 0.5s；**墙会挡光**；锁定角在前摇 55% 处锁死 |
| `summon` | 在身周召唤小怪，计入本房存活数 | 场上敌人 ≥16 时跳过；禁止召唤炮台（会形成永动机） |
| 分裂（数据字段） | 死亡时生成 `splitInto` × `splitCount` | 只允许一层，目标自己不能再分裂 |

激光的判定没有用「矩形重叠」，而是投影 + 垂直距离 + 沿射线采样 `isSolid()`：`along ∈ [0, length]`、`perp ≤ width + player.radius`、中途无墙。这样贴在柱子后面真的能挡住光，而不是被一条穿过墙的线段打到。

BOSS 由 `bossForLevel(level)` 每两层轮换（守卫 / 巨像 / 君王），三套机制分别覆盖弹幕、激光、召唤。刷怪表 `SPAWN_TABLE` 用 `minLevel` 控制解锁：1 层只有哥布林与蝙蝠，炮台和召唤者要到 5~6 层才出现，避免开局劝退。

### 2.12 开始界面：主菜单 / 设置 / 图鉴

原版菜单只是一行「点击画面开始」。现在拆成三个子界面 + 一个帮助页，全部收在 `ui/StartMenu.ts`：

- **主菜单**：4 项（开始 / 图鉴 / 设置 / 操作说明），键盘 `↑↓+Enter`、数字键直达、鼠标点击三条输入路径共用同一份命中检测；背景仍是真实生成的关卡，点开始不加特殊分支。
- **设置**（`data/settings.ts`）：每项声明 `cycle / toggle / action` 与选项表，**存的是选项下标**。消费者对照：`camera` → `cameraLerpOf()` 传给 `Renderer.followRoom`；`screenShake` → `Renderer.shakeEnabled` 总开关；`crosshair` / `minimap` → `HudInfo` 两个布尔门。verify 做源码级检查，删掉消费点会直接失败。
- **图鉴**：武器 / 敌人 / 天赋三页，统一成 `{id, name, color, tag}` 列表视图 + 右侧详情（武器数值与机制、敌人 AI 与每条攻击的前摇/伤害、天赋生效字段）。列表 11 行 + 滚动窗口 `codexOffset()` 保证选中项始终可见。

三条结构性约定：

1. **布局常量与命中检测一起导出**（`menuItemRect` / `hitMenuItem` / `settingRowRect` / `hitSettingRow` / `codexTabRect` / `hitCodexRow`），绘制端与输入端引用同一份坐标 —— 这是天赋面板当年踩过的「画的框和点的框不是同一个」的直接延续。
2. **设置值 = 选项下标 + 读档钳制**。`normalizeSettings()` 对非数字 / 负数 / 越界 / 缺字段统一退回默认；老档（没有 settings 字段）在 `migrate()` 里自动补齐。存下标的好处：改文案、加选项不需要写存档迁移。
3. **前端态在主循环里提前 return**：`menu / settings / codex / help` 四个 mode 只跑 `updateFrontEnd()`（导航 + 鼠标悬停），世界、计时、敌人都冻结；与天赋 / 商店面板同一套路。菜单键盘选中（`menuIndex`）与鼠标悬停（`menuHover`）分开记，鼠标划过不会丢键盘焦点。

**设置页的两种来源**（`settingsReturn: 'menu' | 'pause'`）：设置页本身是四个前端态之一（世界冻结），但它从哪进来决定了 `Esc` 回到哪 —— 从主菜单进的回主菜单，从**局内暂停菜单**进的回暂停菜单、**本局进度完整保留**。关键是 `closeSettings()` 在 `'pause'` 分支只切 mode，绝不调 `backToMenu()`（后者会 `newRun` 重建关卡、清零计时与武器）。这是「同一个设置页、两种返回语义」而不是复制第二份 UI。`activatePause` 的三个动作里只有显式选「返回主菜单」才走 `backToMenu()` → `newRun(undefined, true)`（整局清空、金币**不结算**成宝石，避免「死前白嫖结算」）；死亡界面按 `Esc` 仍直接回主菜单。

### 2.12b 局内暂停菜单与换枪落地

- **局内设置入口**：原来 `P` 只是静态暂停画面、`Esc` 一律 `backToMenu()` 丢本局，玩家想改个准星/震动只能先放弃整局。现在 `P / Esc` 都打开 `Overlay.ts` 的暂停菜单（继续 / 设置 / 返回主菜单），布局与 `hitPauseItem` 同源，键盘 `↑↓+Enter` / 数字键 / 鼠标点击三条路径共用。HUD 右下角常驻 `P / Esc 菜单 · 设置` 提示，`playing` 模式下 HUD 也不再重复画「已暂停」。
- **换枪不丢枪**：`RunState.addWeapon()` 原来在武器栏满 2 把时 `weapons[index] = id` 直接覆盖，被顶替的那把凭空消失。现在它**返回被顶替的 id**（未满填副槽返回 `null`），由 `GameCtx.giveWeapon(id, x, y)` 统一把旧枪掉回地面 —— 落点走 `room.safeSpawn()`（复用 §4 的嵌墙修复），三个来源（地面拾取 / 宝箱 / 商店买枪）只认这一个入口，不会某处漏掉。
- **落地交互锁**：刚掉落的枪带 `dropGrace`（`balance.ts` 的 `weaponDropGrace`）。这层锁同时守在两处：`Pickup.update()` 里 `dropGrace > 0` 不响应按 E、`Game.resolveInteractTarget()` 收集候选时也排除它。少了后者，落地枪 `bias=gear(0.7)` 比传送门优先，会抢走 `interactTargetId` —— 玩家按 E 想进下一层却毫无反应；少了前者，连按 E 会「捡 A→掉 B→捡 B→掉 A」无限对换。保护期结束后自动恢复为普通可捡武器。
- **通知合并**：换枪一帧内会同时发「获得新枪」和「放下旧枪」，HUD 只显示最后一条通知。`giveWeapon` 用 `droppedWeaponId` 暂存，由 `takeDropNotice()` 拼进「获得」播报，避免「已放下 X」被盖掉变成看不见的死代码。

### 2.13 P0~P3：用机制调平衡，而不是继续堆数值

自动试玩暴露的四个失衡（后期偏软 / 资源空转 / 天赋同质 / 武器跨度大），共同点是**纯数值调整已经到边际**：玩家成长是无上限的（天赋每层叠 + 品质武器 + 血量 7→19），敌人只有血/伤两维，继续加斜率只会把前期也变硬。所以这一轮全部走**机制**：

| 维度 | 机制 | 为什么是机制而非数值 |
|---|---|---|
| 后期难度 | 精英词条 `bulwark / swift / armored / volatile`（L6 起按层概率、L14 起双词条） | 改变交战方式：护盾拖 TTK、重甲逼换高伤枪、爆裂惩罚贴脸清场 —— 不靠加血也能让玩家改打法 |
| 后期节奏 | 多波次（战斗房 L10 起 2 波、L18 起 3 波；BOSS 房深层 2 波） | 打断「一波 AOE 全清 + 站着回血」，压力持续而非单点峰值 |
| BOSS 节点 | 半血狂暴（攻速间隔 ×0.7、移速 ×1.2）+ L12 起保底词条 + 护卫 | 给 BOSS 战一个可感知的「阶段转换」，而不是血更厚的木桩 |
| 天赋分布 | `talentDecay(stacks)=0.82^stacks` 同类递减 + `diversifyByTag` 跨类轮询 | 递减同时给「玩家成长」加天花板，反向治后期倒挂；跨类让一次四选一真的覆盖不同维度 |
| 资源经济 | 金币掉落收敛 + 商店 `price×1.06^(层-1)`；能量池 200→110 + 补给球产出砍 76% | 治「收入 >> 消耗」这个共同病根 |
| 武器跨度 | 评分纳入机制/射程/能量可持续性；弱武器补机制、强武器回收 | 旧评分把近战无条件 ×1.3 且不计机制，跨度 10x 是「评分口径」而非真实强度 |

**单一事实源**：`talentDecay` 同时被 `RunState.applyTalent`、机器人 `talentScore`、`verify` 测试引用；`eliteChance / rollAffixes` 同时被 `Room.spawnContents` 和压测引用 —— 避免「数值三处各算一套」。

**可测性**：`Room` 暴露 `waveCount / eliteCount` 只读字段（而非让统计脚本去读 private `pendingWaves`），`Enemy.isElite` 由 `affixes.length` 派生。压测把「性质」而非「具体数值」锁死：精英概率低层为 0/单调递增/有上限、多波次随层 1→2→3、天赋递减严格递减且成长有上限、4 候选覆盖 ≥3 类、定价随层严格递增、武器跨度 ≤4x。

**一个反例（诚实记录）**：P1 最初把回能 11→9.5 想让「饥饿率回升」，结果饥饿率归零。8 局加指标实测后才明白：饥饿率只统计「连一发单发成本都扣不起」的帧，在 200 点大池下结构性为 0，它照不出能量经济；真正的杠杆是**缩池 + 削补给球**。所以本轮把试玩指标从「饥饿率」换成「能量水位（战斗中 energy/maxEnergy 的均值/低水位占比）」，并把 `balance.ts` 里那段基于错误假设的注释按实测重写 —— 指标选错比数值调错更危险，因为它会让你以为改对了。

## 3. 主循环

```
requestAnimationFrame
  └─ 累加器 → 固定步长 1/60（最多 5 子步）
       ├─ input.aim = renderer.toWorld(鼠标)
       ├─ [menu / settings / codex / help] updateFrontEnd() → 只处理导航与悬停，世界冻结，然后 return
       ├─ [paused] updatePauseMenu() → 冻结世界与计时，只处理暂停菜单导航，然后 return
       ├─ [talent / shop] updatePanel() → 冻结世界与计时，只消费 1~4 / 点击 / Esc，然后 return
       ├─ [playing] elapsed += dt；levelElapsed += dt
       ├─ player / weapons / enemies / projectiles / pickups / particles
       ├─ room.update()  ← 统计本房存活敌人，归零即 clear
       ├─ room.doorAt()  ← 踩门 → enterRoom（传送 + snapToRoom 对齐相机）
       ├─ renderer.followRoom()  ← 相机缓慢跟随玩家（目标按房间边界钳制）
       ├─ 各池 sweep()
       └─ pendingNextLevel（帧末）→ 每层（talentInterval=1）先 openTalentPanel() 挂起，选完再 doNextLevel()
  └─ draw(): begin → level → entities → end → ui(HUD → 面板/Overlay → F3)
```

`justPressed` 只在第一个子步生效，防止一次按键被固定步长循环消费多次；但它对本步**所有**实体都返回真，所以 E 交互另外需要 `resolveInteractTarget()` 先仲裁出唯一目标，见 §4.1。`nextLevel()` 只置标志位，帧末再换层——因为传送门是在 `pickups.forEachActive` 里被触发的，当场清空池会破坏迭代。天赋面板把「要进的层号」暂存在 `pendingLevel`，选完再继续，所以计时在玩家做选择时是停住的。

## 4. 踩坑清单（每条都在代码里有对应处理）

| 坑 | 后果 | 处理 |
|---|---|---|
| 主干允许斜向步进 | 两房斜对角、无共享墙 → 挖不出门 → 楼层不可通关 | `foreignNeighbours() === 0` + 只走正交步 |
| 新房间触碰主干非前驱格 | 多开一道门 → 绕过战斗的捷径，不报错、楼层悄悄变短 | 候选格只与前驱相邻，门图压成树 |
| `Array.sort(() => Math.random())` 打乱 | 同种子重建不出同一张图 | `RNG.shuffle()` 自带 Fisher-Yates，吃注入的 rng |
| 模板外圈是墙 | 门被堵死 | `RoomTemplate.problems()` 自检 |
| 模板内部不连通 | 敌人被困在口袋里 → 房间永远清不掉 | 同一自检做 BFS 连通性校验 |
| 敌人用「矩形内随机点」生成 | 柱子出现后会落进墙里 → 卡住打不死 | 只用 `walkableTiles(2)`，距边界 ≥ 2 格 |
| 格子坐标 off-by-one | 生成点错位、门开在地板上，**逻辑测试全绿** | 统一约定：layer 0 / size+1 是墙环，模板 (x,y) → layer (x+1,y+1) |
| 门触发框正好嵌在墙里 | 玩家身体只与门相切 → 门时灵时不灵 | 触发框跨墙与地板、半径 1.15 TILE |
| 「房间被清空」当作过关条件 | 宝箱房没有敌人，生成瞬间整层被判通关 | 过关 = 玩家走进已清空的出口房 + 交互传送门 |
| 参数被认真赋值但没人读 | 护盾 0.02 秒回满、速度随帧率变，测试还全绿 | `armorRegenRate` 在 `Player.update` 有真实消费者；F3 浮层显性化 |
| 对象存在 ≠ 路径可用 | 「测试断言单例非空」全绿，但主菜单点开始黑屏 | `validatePlan()` 走真实可达性，F3 显示结果 |
| 定义分散在两地 | 升级卖出去却从没生效，全程不报错 | 升级表、武器表都收拢为单一数据源 |
| 瞄准方向被移动方向覆盖 | 后退射击这个核心技巧消失 | `aim` 每帧独立由鼠标世界坐标计算 |
| 无敌帧短于翻滚 | 「我明明滚了却挨打」 | `rollInvuln (0.34) > rollDuration (0.28)` |
| 死亡把永久成长清掉 | 玩家白花宝石 | RunState / GameState 分离 |
| 保证房混在普通分支里抢位置 | 受 `foreignNeighbours` 树形约束，53% 的层没有商店、66% 没有奖励房，玩家看不到新内容且**完全不报错** | 三层防线（结构性保证 / 硬契约 / 常驻压测），见 §4.1 |
| 一次 E 消费多个交互物 | 根因是 `justPressed('KeyE')` 对本步**所有** pickup 都为真，站中间一次按键把宝箱和神龛一起领走；拉开距离只是缓解，拾取范围天赋一放大就失效 | `core/interaction.ts` 的 `pickInteractTarget()` 每步只放行最近的一个，经 `GameCtx.interactTargetId` 下发；拉开距离降级为纯体验优化 |
| 天赋倍率只赋值不读取 | 「加了天赋但没变强」，测试还全绿 | 每个倍率都有真实消费者；`applyTalent` 的 `switch` 用 `never` 穷尽检查兜住「加 stat 忘接」；`npm run verify` 逐条应用 27 条天赋，断言字段确实变化，并对 3 个新 stat 做源码级消费者检查 |
| 武器与传送门重叠 | BOSS 掉落武器落在尸体处、传送门在房间正中，二者常相距十几像素；只按距离仲裁 → 想捡枪却被传进下一层，**不可逆**，武器直接丢失 | `score = 距离² × bias`（装备 0.7 / 传送门 1.5），重叠时装备必胜；BOSS 掉落再推离中心 ≥3.5 格做视觉保险。压测锁死三种距离关系 |
| 每层都弹天赋但候选重复 | 池子仅 12 条、纯随机三选一，几层后反复出同一批，选择毫无意义 | 27 条池子 + `rollTalentChoices()` 优先未拥有 + 4 候选，前 6 层不重复 |
| 面板期间继续跑世界与计时 | 选个天赋白送几秒，甚至被敌人打死 | 面板态在 `update()` 提前 return，只处理输入 |
| 面板点击被当成按住开火 | 关掉面板后角色自动连发 | `toUI()` 做命中检测，切面板时 `input.firing = false` |
| UI 卡片绘制与点击各写一套坐标 | 点第一张卡却选中第二张 | `cardRect()` / `hitCard()` 同源布局常量 |
| 菜单选项按住开火直接开始游戏 | 主菜单里点一下鼠标 = 无条件开局，菜单选项形同虚设 | `onPointerDown()` 统一路由：menu 模式只接受命中 `hitMenuItem` 的点击 |
| 键盘焦点被鼠标抢走 | 鼠标划过菜单后 ↑↓ 选不中想要的项 | `menuIndex`（键盘）与 `menuHover`（鼠标）分开记，高亮取并集 |
| 设置存布尔/字符串，加选项要写迁移 | 老档读出新类型直接崩 | 存「选项下标」，`normalizeSettings()` 读档钳制，越界/缺字段退默认 |
| 设置项存了没人读 | 滑块永远不生效，玩家以为是自己不会用 | verify 源码级检查：camera→Game、screenShake→Renderer、crosshair/minimap→HUD |
| 静态绘制的 UI 截图截不到 | 无头浏览器里画布合成器拿不到单次绘制的新帧 | 开发期核对排版时用 rAF 循环重画（游戏本体本来就持续出帧，不受影响） |
| 计时标签画在负 y | `oy - 15 = -3`，文字被裁掉，还以为没渲染 | 改到小地图框下方 |
| 相机锁房间中心 | 房间比视口高（432 vs 270），玩家走到南北门时连人带门出屏，「看不到出口」；12% 偏移只补 25px，缺口还有 48px | `cameraTarget()` 分轴跟随 + 钳制，`followRoom()` 指数平滑 |
| 相机完全自由跟随 | 一层只画当前房间，镜头把大片空背景带进画面 | 视口按房间边界钳制；比视口窄的轴锁中心 |
| 过门后相机从旧位置插值 | 玩家被传送到对侧门，相机要飞 ~300px，期间玩家出屏 | 切层 / 过门用 `snapToRoom()` 直接对齐，只有房间内才用平滑 |
| 品质色散落在各页面 | HUD 是蓝的、掉落物是紫的，改一档要改四处 | `rarityColor()` 是唯一来源；页面不写任何品质色值 |
| 爆炸弹又结算直击又结算 AoE | 同一目标吃两份伤害，调数值时看不出伤害来自哪一份 | 命中即引爆并 return，只由 `explode()` 按阵营结算一次 |
| 抽到空的品质池 | `rng.pick([])` 返回 undefined，一路传到 `addWeapon()` 才炸 | `rollWeapon()` 三级降级：品质不可用 → 该档无武器 → 退手枪，永远返回合法 id |
| 远程攻击没有前摇 | 玩家看到子弹时已经掉血，无法躲避 | 回归断言所有 `windup > 0`；激光额外要求 ≥0.5s 并画预警线 |
| 激光判定用矩形 / 射线不查墙 | 躲在柱子后面仍被光束打到 | 投影 + 垂直距离 + 沿射线逐段 `isSolid()` 采样，墙真的挡光 |
| 召唤 / 分裂没有上限 | 数量指数增长，帧数和难度一起崩 | 召唤受场上敌人数上限（16）；分裂目标自身不允许再分裂 |
| 新增敌人忘画精灵 | `sprite()` 静默画洋红圆，不报错，靠肉眼才发现 | `SpriteAtlas.SPRITE_IDS` 是唯一清单，回归断言敌人 / 掉落物全覆盖 |
| 弹墙只翻转整体角度 | 斜射进墙角时两轴都卡住，子弹原地抖动 | 分轴判断，只翻转被挡住的那一轴分量，角点才整体反向 |
| 切枪继承上一把的冷却 | 刚打完轨道炮（1.1 发/秒）切到手枪，还要等 0.9 秒才能开火，切枪失去意义 | `WeaponSystem` 用 `Map<武器 id, 剩余冷却>`，每把武器独立计时，切枪立刻可用 |
| 生成点只判「格子可走」 | BOSS 半径 13~14 比一格还宽，吸附到「可走格」仍 43.7% 嵌在柱子里：出不来、打不到、房间永远清不掉，整局静默卡死 | `Room.safeSpawn(prefer, radius)` 逐格验证 `collides(x,y,radius)`；BOSS/怪/商人/宝箱/传送门/掉落全部走它；1200 关压测锁死 0% |
| 开火点在玩家身侧 10px | 贴脸时枪口直接落在敌人体内，子弹第一步位移就跨过目标中心 —— 磁暴炮连打 2 发 0 伤害 | `Projectile` 出生帧先 `checkHits()` 一次再位移；`npm run verify` 有「贴脸开火能打中」四武器用例 |
| 敌人不随层数成长 | 30 局自动试玩 0 死亡，每层受伤 L6 15.3 → L30 3.0，越打越轻松（难度曲线倒挂） | `Enemy.applyLevelScale(level)`：血量 +10%/层、伤害 +5%/层；**伤害只走 `hitPlayer` 一个出口**，缩放点集中 |
| 用「死亡率」判断难度 | 同一份代码连跑两次，30 局死亡数 0~4 抖动，结论跟着随机 | 难度看「每层平均受伤」曲线与「层用时」，不看死亡率 |
| 只加敌人血/伤治后期偏软 | 玩家成长无上限（天赋叠加 + 品质武器 + 血 7→19），斜率只能补一半，且把前期也变硬 —— 仍是「数值墙」 | 精英词条 / 多波次 / BOSS 狂暴三件机制，改变交战方式而非加数值；L30 受伤 5.7→12.8 |
| 天赋纯数值无上限叠加 | 四件套（capacitor/battery/bulwark/berserk）霸榜，且玩家成长无天花板 —— 正是后期倒挂的病根 | 同 stat 递减 `0.82^stacks`（30 次伤害天赋收敛到 7.47）+ 候选跨类轮询；27 条全覆盖、top4 占比 23% |

| 武器评分口径自带偏差 | 近战无条件 ×1.3 且不计能量，前 6 名 5 把近战、破锈短剑碾压磁暴炮，跨度 10x 是评分假象 | 评分纳入机制/射程/能量可持续性；弱武器补机制、强武器回收；跨度 10.3x→3.3x |

### 4.1 「静默缺失」的三层防线

早期 `placeGuaranteed()` 只是把两个保证房挪到主干上抢位置，压测 100% 是**运气**不是保证，三个缺口叠在一起才构成「完全不报错」：函数找不到空位时直接 `return`，什么都不报；`validatePlan()` 也不检查保证房存在与否，F3 永远显示 OK；一次性压测脚本跑完就删，下次改 `mainLen` / `GRID` 会悄悄退化，没人发现。现在改成：

1. **生成时结构性保证**：`GUARANTEED_TYPES` 是单一事实源（生成器 / 自检 / 压测共用，避免三份名单漂移）。一次性收集整条主干的全部合法空位并打乱，两个保证房公平取位、不再串行抢，每次取位前重新跑 `legalSlot()` 校验。所有房间生成完后统一兜底 —— 仍缺就把一个普通战斗 / 宝箱房**就地改类型**（不加格子、不加门，树形门图不变），末尾还有 fail-fast 断言。所以无论网格多挤都恰好各一个，`LevelPlan.fallbackCount` 记录降级次数。注意挂点必须是**整条主干**：中段战斗房被链夹住，四周空格全被 `foreignNeighbours>0` 排除，只挂中段会让取位几乎必然失败、退化成全量改类型。
2. **运行时硬契约**：`validatePlan()` 新增「门连正交相邻格」「边数 = n-1（门图是树）」「保证房恰好各一个且非起终点」「`requiredBattles` 与实际战斗房一致」。任何退化都会在 F3 浮层显性报错，不再沉默。
3. **可重复回归**：`npm run verify` 常驻，2880 关（常规 200 种子 × 12 层 + 3 组极端参数 480 关）+ 交互仲裁 8 项单测（含 3 项优先级权重）+ 相机跟随 5 项单测（255 采样点）+ 天赋系统 6 项（抽取策略 / 27 条逐条生效 / stat 消费者 / 面板布局）+ 武器与品质 7 项（配置自洽 / 配色唯一 / 层数门槛 / 掉落池合法）+ 敌人 4 项（配置 / 解锁层 / 后期怪 / BOSS 轮换）+ 精灵覆盖 + 开始界面与设置 12 项（按钮命中 / 设置循环与坏档钳制 / 设置消费者 / 图鉴滚动与命中）+ 武器机制实跑 5 项（弹墙 / 爆炸 / 引信 / 追踪 / 阵营）+ 运行时冒烟 12 项（真实 Game 跑 1200 帧 / 24 把武器逐把开火 / 激光 / 召唤 / 玩家掉血 / 开始界面全链路：进设置改项写档、关震动后 shake 失效、图鉴三页、Esc 回主菜单重置本局）+ 同种子可复现校验。极端参数专门用来逼出降级兜底，确保这条路径本身被测到，而不是「理论上能兜住」。实测常规 2400 关零降级、压力用例 239 关触发兜底且自检仍零异常。

配套地，「一次 E 双消费」也从**空间规避**改成**逻辑仲裁**：`pickInteractTarget()` 是纯函数，每逻辑步从范围内候选中返回唯一一个 id（按 `距离² × bias` 排序，见 §2.9），Pickup 只有 id 匹配才 `collect()`。奖励房把宝箱 / 神龛放到可走格里距离最远的一对，仅剩「提示文字别叠一起」的体验作用。同理，相机目标与交互仲裁都刻意做成不依赖 DOM / Canvas 的纯函数，才能进同一套 Node 回归 —— **「靠肉眼在浏览器里看一眼」不算验证**。

## 5. 与原作的差距 & 可扩展点

脚手架刻意停在「一局能打完、结构完整」的程度。下面这些是明确的下一步，接口都已经留好：

- **技能 / 雕像 / 因子**：天赋四选一（每层都能选）已完整落地（27 条数据表 → 面板 → 倍率消费链 → 压测），角色主动技能仍留 `CharacterData.skillName` 字段待接入状态机；主菜单已留出「选角色」入口位（`MENU_ITEMS` 加一项即可）
- **设置扩展**：`data/settings.ts` 是配置表 + 消费者对照，加音量 / 语言 / 按键重映射只需要加条目和消费点；`setSettings()` 是唯一写入口
- **计时榜 / 分段计时**：目前只有「最快单层」，可扩成每层分段记录与结算页榜单，`SaveData` 已留迁移分支
- **BOSS 阶段**：`attacks[]` 已支持多套攻击轮换（守卫 / 巨像 / 君王各有 2~3 套），但真正的「血量阶段」——50% 血换招、进狂暴、清场一次——还需要在 `Enemy` 加一个 `phase` 字段，按 `hp / maxHp` 切 `attacks` 子集
- **2D 灯光**：`Renderer` 的绘图原语已分层，加一层 `CanvasModulate` 式的暗色叠加 + 点光最划算
- **相机前瞻 / 视野偏移**：`cameraTarget()` 已把玩家位置、视口、房间解耦，加一个朝瞄准方向的 look-ahead 只需在目标上叠加偏移，仍走同一套钳制
- **手柄双摇杆**：`Input.moveAxis()` 与 `aim` 已分离，右摇杆只需写 `aim` 并优先于鼠标
- **联机 / 中断续跑**：续跑要把 `RunState.to_dict()` 落盘，且**必须同时存 `levelSeed`** 才能重建同一层
- **编辑器手搭房间**：ASCII 模板适合迭代期，布局定型后应转成可视化场景数据
- **行为树 AI**：敌人变多后把 `_steer()` 换成 Beehave / LimboAI 之类的行为树
